# Contributing to dsh-trajectory

Thanks for your interest. This document explains how to set up a development
environment, run the test suite, and submit a change.

## Code of conduct

By participating, you agree to abide by the [Code of Conduct](./CODE_OF_CONDUCT.md).

## Reporting issues

- **Bugs and crashes**: open a [Bug report](../../issues/new?template=bug.md).
- **Feature requests**: open a [Feature request](../../issues/new?template=feature.md).
- **Questions / how-to**: open a [Question](../../issues/new?template=question.md).
- **Security issues**: **do not** open a public issue. Follow [SECURITY.md](./SECURITY.md).

## Development setup

Requirements:

- Node.js **>= 18.18** (we test on 18, 20, 22 in CI).
- A C/C++ toolchain capable of building `better-sqlite3` native bindings.
  - Linux: `build-essential` + `python3`.
  - macOS: Xcode Command Line Tools.
  - Windows: Visual Studio Build Tools with the "Desktop development with C++" workload.

Clone and install (no global writes):

```bash
git clone https://github.com/kaijie-czyh/dshExplore.git
cd dsh-trajectory
npm ci
npm run build
npm test
```

## Project layout

```
src/
  core/        # framework-free logic (events, store, replay, diff)
  plugin/      # Cordis plugin entry
  cli/         # commander-based CLI
  web/         # self-contained Compare HTML
test/          # node:test smoke tests
examples/      # synthetic JSONL session events
.github/       # issue/PR templates + CI workflows
```

Anything under `src/core/` is intentionally framework-agnostic so the same
codebase can be reused from the Cordis plugin, the CLI, tests, and downstream
tools.

## Commit & branch conventions

- Branch names: `feat/<short-topic>`, `fix/<short-topic>`, `chore/<short-topic>`.
- Commit messages: short imperative summary, optional body explaining *why*.
- One logical change per commit; keep diffs reviewable.

## Pull request checklist

The PR template will prompt you for:

1. `npm run build` exits 0.
2. `npm test` exits 0.
3. New behavior is covered by a `node:test` case under `test/`.
4. If you touched the public event shapes, updated `src/core/events.ts` and
   documented the change in `CHANGELOG.md`.
5. If you added a CLI subcommand, it appears in `--help` and in `README.md`.

CI runs the same checks on Node 18, 20, and 22.

## Versioning & release

We follow [Semantic Versioning](https://semver.org/). Breaking changes to the
event shapes (`SessionEvent`) require a major bump because downstream users
may import these types.
`npm run release` (maintainer-only) bumps the version and tags the commit;
do **not** run `npm publish` locally — release is performed from CI on a clean
tagged tree.

## Style

- TypeScript strict mode is enabled; do not weaken it.
- Keep `dist/` clean: it is regenerated by `npm run build` and must not be
  edited by hand.
- Avoid pulling in new runtime dependencies unless they pull their weight.
  The current runtime set is `better-sqlite3` and `commander` and that's it.
